**Implementation notes:**
- *Celery is real now.* `config/celery.py` (autodiscover, `CELERY_` settings namespace) is imported from `config/__init__.py`; broker/result = `REDIS_URL`, and when that is unset (dev `runserver`, unit tests, CI's SQLite job) `CELERY_TASK_ALWAYS_EAGER=1` runs tasks in-process so nothing silently queues into a broker that isn't there. `CELERY_BEAT_SCHEDULE` holds `run-retention-daily`; docker-compose gained a `beat` service next to the (now actually startable) `worker`. Proven end-to-end on the compose stack: `run_retention_task.delay()` from the backend container was received and executed by the worker over Redis against Postgres.
- *Retention executor* — the Sprint 2 `RetentionRule` model finally has a job. `rbac_audit/retention.py` is a **handler registry**: each app registers a handler for its own `app_label.ModelName` from its `AppConfig.ready()` (`rbac_audit` for `AuditLogEntry`/`StepUpGrant`, `recruitment` for `Applicant`), so the executor never imports a peer app; a rule with no handler is reported as `no_handler`, never guessed at (a generic "delete anything older than X" across arbitrary FKs is exactly what must not run unattended). Every real execution writes one `AuditLogEntry` per rule (`DELETE`/`UPDATE`, actor=None, count in `fields_touched`); `--dry-run` changes and logs nothing. Migration `rbac_audit/0007` seeds defaults: audit log **retain** (deleting audit history is HR's decision, not a default), step-up grants purge after 1 month, rejected applicants anonymise after 12 months (the Data Dictionary's own example — `recruitment/retention.py` blanks identity fields, sets a `1900-01-01` DOB sentinel, clears free-text stage notes, purges the simple-history rows that would otherwise still hold the PII, keeps stage outcome + demographics for aggregate EE recruitment stats, and stamps the new `Applicant.anonymised_at` so it is idempotent).
- *Throttling* (`rbac_audit/throttling.py`) — login is throttled per source IP (30/min burst, 500/hour sustained) **and per submitted username** (10/min); IP-only limits are useless against a slow distributed guess at one account and, behind a corporate NAT, far too tight for an office logging in at 08:00 — the per-username key is what actually protects an account. TOTP confirm and the step-up challenge are keyed per user (5/min burst, 30/hour sustained): a 6-digit code with `valid_window=1` is ~3 valid codes per 30 s, and 30/hour turns an online brute force from "slow" into "impractical". Rates are env-tunable (`THROTTLE_*`); counters live in `CACHES` — Redis when `REDIS_URL` is set so all gunicorn/celery processes share them, LocMem otherwise. Existing auth/step-up tests gained `cache.clear()` in `setUp` because throttle state now legitimately persists across requests.
- *Reproducible builds* — `requirements.lock` (pip-compile, `--strip-extras`) is what the Dockerfile and both CI backend jobs install; `requirements.txt` stays the human-edited direct-dependency list. A "lock is in sync" CI step was tried and dropped on purpose: it would go red whenever PyPI publishes a new patch between compiles, which is the exact failure mode the lock exists to prevent.
- *Postgres in CI* — a second backend job runs `migrate` + `seed_demo_data` + the full suite against `postgres:17` (the production engine); the SQLite job stays for speed. The seed step is deliberate: it writes to every app's models, so engine-specific surprises surface even where a test doesn't.
- *Compose/prod shape* — new `frontend` service (multi-stage node → nginx; `nginx.conf` serves the SPA with history-API fallback and proxies `/api`, `/admin`, `/healthz`, `/static` to `backend`; hashed `/assets` cached immutable, `index.html` never). Media is **not** served by nginx — Django's authenticated `download` endpoints stay the only path to uploaded files. Backend `expose`s 8000 instead of publishing it. Settings: `SECURE_PROXY_SSL_HEADER`/`USE_X_FORWARDED_HOST` when `DEBUG=0` (without them the SSL redirect loops behind a TLS-terminating proxy), `DJANGO_SECURE_SSL_REDIRECT` env switch for plain-http LAN pilots. Two compose bugs found only by actually running the stack: the `media` named volume was root-owned so the non-root `appuser` could not write uploads (`seed_demo_data` failed) — Dockerfile now creates `/app/media` owned by `appuser` before `USER` so a fresh volume inherits it; and nginx's `/healthz`/`/static` locations weren't forwarding `Host`, so Django's `ALLOWED_HOSTS` rejected them with 400.
- *Global session-expiry handling* (`api/client.ts` → `AuthContext.sessionExpired` → `RequireAuth` → `LoginPage`) — DRF's `SessionAuthentication` answers a dead session with **403**, not 401 (same status as a real permission denial), which is why a naive 401 hook did nothing in the browser. The client now treats 401 as session-lost outright and, on 403, re-probes `/auth/me/` once (deduplicated across concurrent requests) before declaring the session gone; the provider clears the user, `RequireAuth` redirects to `/login` carrying `state.from`, and the login page shows "Your session expired…" then returns the user to where they were.
- Docs: `adr/ADR-007..009` files added (previously table rows only), `rbac_audit/tiers.py` stale reference to a non-existent `performance/permissions.py` fixed, README module rules reworded so the tiering sentence says which models `FIELD_TIERS` actually covers and the Celery rule says what is actually true, `hcm/frontend/README.md` replaced.

**Architecture / design tension:** the retention job is the first thing in the codebase that *acts* on data unattended, so the design errs entirely toward "refuse to guess" — registry over reflection, dry-run first, per-rule isolation, audit entry per run, safe seeded defaults. The throttle design accepts one deliberate weakness: per-username limits can be used to lock a known user out for a minute from anywhere; that is preferable to the alternative (no per-account limit at all), and django-axes-style progressive lockout with an unlock path is the C-series follow-up if it bites in UAT.
