**Status: in progress** (2026-08-19, commit `1b96b11`; all six functional pieces now done, docs-split cleanup done 2026-08-20 — only the `api/types.ts` swap remains) — H3 turned out to be six largely-independent pieces bundled under one banner (confirmed by research before starting: notifications, audit viewer, data-quality, EEA validation, ops/observability, OpenAPI, docs). **Implementation notes:**
- *One write path, every consumer.* `notifications.services.notify()`/`notify_many()` is the single call site every domain app uses — in-app is unconditional (a `Notification` row always exists), email is best-effort on top and never breaks the caller's own transaction if the mail server is down (same "outbound is best-effort" rule `integrations.collab` already follows). `notifications` joined `SHARED_KERNEL` in `rbac_audit/test_module_boundaries.py` on the same reasoning `integrations` did in PC-0 — it knows recipients and message text, nothing about agreements/proposals/policies as domains.
- *Email adapter is SMTP, not Graph* — sufficient for every consumer wired so far; a Graph-specific backend is a drop-in `EMAIL_BACKEND` swap later since callers only ever see `notify()`. No `SMTP_HOST` set (local dev/tests/CI, the default) → Django's console backend, so nothing blocks on a real mail server.
- *PC reminders* gained a genuinely independent second channel, not a copy of the collab push: in-app fires for every outstanding employee (no `collab_user_id`/department mapping needed, unlike the collab path), with its own idempotency key (`{key}:in_app`) alongside the existing `ReminderLog` row, so a rerun never double-notifies either channel, and `dry_run` correctly touches neither.
- *Review launch* (`open_phase`) notifies every employee whose agreement just moved to an `*_open` status, evaluated before the caller's own `.update()` runs the status transition (an `.update()` queryset can't be iterated for recipients afterward). *EE sign-off* (`sign_agreement`) notifies the other signatory: the Head when the employee signs, the employee once the Head completes it.
- *Policy publish* has no audience-targeting fields on `Policy` (unlike `AgreementTemplate`), so it's a genuine broadcast to every currently-employed person via `notify_many` (bulk-created, not N individual queries) — confirmed by re-running seed data itself, which already calls `publish_policy` three times and now notifies every seeded employee as a side effect, exactly as production would.
- *Liveness flag* has no single natural recipient (unlike a signature or a proposal), so `employees_with_role("hr_admin")` — a small new shared-kernel helper — is the broadcast target, reusable anywhere else a role-wide notification is needed later (the audit-viewer's own future backlog item, most likely).

**A defect found by verification, fixed:** the first cut of the PC-reminders in-app channel fired unconditionally, including during `dry_run=True` — `test_dry_run_touches_nothing` caught it immediately (a dry run is supposed to be a preview, not a partial send). Fixed by gating both new `notify()`/`_record()` calls behind `not dry_run`, matching the existing collab-path guard.

- *The TS-generation half hit a real tooling gap*: `openapi-typescript` 7.13.0 calls the TypeScript compiler API directly (`ts.factory.createKeywordTypeNode`) and breaks under this project's TypeScript 7 (`~7.0.2`) — `Cannot read properties of undefined`, since Node module resolution hands it the nearest `typescript` package (this project's 7.x) over its own declared `^5.x` peer. No published version supports TS 7 yet. Fixed by isolating the codegen tool in its own `tools/api-codegen/` directory with its own `node_modules` pinned to `typescript@^5.7`, so it never sees the parent project's TS 7 — `npm run generate:api-types` (from `hcm/frontend`) orchestrates both steps (`manage.py spectacular` → schema JSON → `openapi-typescript` in that isolated scope → `src/api/generated-types.ts`). The generated file (13,173 lines, every docstring carried through as JSDoc) type-checks cleanly under the *project's* TS 7 even though a TS 5 tool wrote it — proving the pipeline works end to end.

**H3 slice 6 (EEA export cell-by-cell validation), done 2026-08-19** — `ee_reporting/validation.py::validate_report_data(report)` (new), a companion to Sprint 13-14's `validate_report_readiness` (which gates GENERATION on data being *available*; this gates review/sign-off on the frozen `data` itself actually being *correct*, since an aggregation bug or source data that changed between "ready" and "generate" can't be caught by a pre-generation check). Covers 5 of the 6 checkable rules confirmed in `EEA-Form-Spec-Notes.md` #7 directly: (1) matrix completeness — every row×column present and a non-negative whole number, not blank/None/negative; (2) aggregate-row arithmetic — `total_permanent` really is the sum of the occupational-level rows, `grand_total` really is `total_permanent + temporary_employees`, per column, per matrix; (3) integer-Rand formatting — every remuneration-shaped figure in an EEA4 snapshot (`total_remuneration`, `highest_paid`/`lowest_paid_lowest_level`, `median_and_gap`) is a whole int, not a float; (4) EEA2↔EEA4 cross-form headcount consistency, applied to the two *frozen* snapshots themselves rather than live data (extends the existing pre-generation check, which only compares a candidate EEA4 against live aggregation); (5) Section F's 24-category barriers/AA-measures grid — every category has an actual Y/N for both `barriers` and `aa_measures`, not silently missing. The remaining two rules are addressed by a documented scope decision rather than new storage: annualisation isn't independently re-checkable (`RemunerationRecord` stores only the final annualised figure, not raw pre-annualisation earnings or months-worked — the CSV import is explicitly a stand-in for a real SAP extract, ADR-006), and "% row computation" isn't a separate check (this system's exports report values only, per `export.py`'s own existing note about not being a pixel-perfect form recreation — percentages are a trivial derived function of the values, so their correctness is fully covered by the arithmetic check). A sixth, employee-data-correctness check was added beyond the matrix rules: **temporary classification** — `employment_status=TEMPORARY` ("< 3 months") is a manually-chosen field with no separate contract-duration column, cross-checked against how long the employee's version has actually been open as of the report's `period_end`; anything open ≥90 days gets flagged.
