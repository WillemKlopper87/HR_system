## Step-Up Authentication for Payroll Data (unplanned addition, ADR-009)
**Goal:** Viewing Restricted-tier payroll data should require more than just holding the comp_manager/hr_admin role — a step-up MFA challenge plus a mandatory, selected business-justification reason, both logged. Requested 2026-08-13, modelled explicitly on Windows Server's shutdown-reason prompt.
**Status: done** (2026-08-13) — see `rbac_audit/stepup.py` (service layer + `RequiresStepUpGrant`/`RequiresPayrollStepUp` permission classes), `rbac_audit/models.py::TOTPDevice`/`StepUpGrant`, and `hcm/frontend/src/auth/RequirePayrollStepUp.tsx` (the enrollment + challenge UI, wrapping `PayBandsPage`, `CompProposalsPage`, and `EEConfigurationPage`'s remuneration section specifically — not the whole EE configuration page).

**Tasks:**
- [x] Scope which data this actually covers — Data-Dictionary.md tiers exactly three models "R" (Restricted) with real salary figures: `compensation.pay_band`, `compensation.comp_proposal`, and `ee_reporting.remuneration_record` ("imported from SAP payroll" — the most literal payroll data in the system). `recruitment.Offer`'s pay fields are also "R" but mixed onto a model with non-pay fields (applicant, status, dates) — gating the whole `OfferViewSet` would block recruiters from even seeing an offer's status without MFA; left explicitly out of scope, noted as a follow-up needing field-level (not viewset-level) gating.
- [x] TOTP-based step-up MFA — `rbac_audit.models.TOTPDevice` (one per employee, RFC 6238 via `pyotp`), enrollment is (re)startable at any time (a lost-device recovery path, not a one-shot); `POST /api/v1/auth/totp/enroll/` → `POST /api/v1/auth/totp/confirm/` with the first code activates it.
- [x] Business-justification reason, required together with the code — `StepUpGrant.Reason` (payroll processing/audit, employee query, compliance reporting, system troubleshooting, other-with-required-detail); `POST /api/v1/auth/step-up/` is the single call that verifies the TOTP code AND records the reason — there's no way to satisfy the MFA check and the justification requirement as two independently-replayable steps.
- [x] Time-boxed grant, not a permanent unlock — `StepUpGrant.expires_at` (15 minutes, `STEPUP_GRANT_MINUTES`); re-requesting after expiry needs a fresh code and a fresh (possibly different) justification, so a grant obtained for one stated reason can't quietly cover a whole day's unrelated browsing.
- [x] Every grant audit-logged — `AuditLogEntry.Action.STEP_UP_GRANTED`, same `log_access()` mechanism every other Restricted/Sensitive-tier access already uses, `field_tier=RESTRICTED`, `fields_touched="scope=...;reason=..."`.

**Design shape — a permission class layered on top, not instead of, the existing role check:** `RequiresPayrollStepUp` sits alongside `IsCompManagerOrHRAdmin`/`EEReportingPermission` in each viewset's `permission_classes` list (DRF requires every listed class to pass — AND semantics, not OR). Holding the role is still necessary; it's no longer sufficient on its own for these three models. `PayBandViewSet`/`CompProposalViewSet` (compensation) and `RemunerationRecordViewSet` (ee_reporting) all gained it; `BenefitViewSet`/`BenefitsElectionViewSet` (Sensitive, not Restricted, and already read-open per Sprint 15) and `EEReportViewSet` (Sensitive-tier aggregated *snapshots*, not raw per-employee figures) deliberately did not. Report *generation* (`ee_reporting.services.generate_report`) reads `RemunerationRecord` directly at the ORM layer, not through the gated viewset, so a signed-off EEA4 report isn't blocked by whether anyone currently holds a step-up grant — only the raw record-browsing/CSV-import UI is.

**Frontend shape:** `RequirePayrollStepUp` is a children-wrapping component (not a route-Outlet guard like `RequireRole`, since it needs to render an interactive enrollment/challenge form, not just redirect), used two ways: wrapping the entire route element for `/pay-bands` and `/comp-proposals` (both pages are payroll data end to end), and wrapping only the `RemunerationRecordsLoader` sub-component inside `EEConfigurationPage` (Employer Config and the EE Questionnaire on that same page are Internal-tier, not Restricted, and must keep loading even without a payroll grant — a real bug caught before it shipped: the page's original single `Promise.all` fetched all three sections together, so a `RemunerationRecord` 403 would have failed the whole page).

**Acceptance criteria:**
- [x] Holding comp_manager/hr_admin alone no longer grants access to PayBand/CompProposal/RemunerationRecord — a fresh privileged user with no step-up grant is blocked. — `PayrollStepUpGateApiTests`, `RemunerationImportApiTests.test_hr_admin_without_step_up_grant_is_blocked`
- [x] A valid TOTP code plus a selected justification reason together unlock access for a bounded window. — `StepUpRequestApiTests`, browser-verified with a real client-side RFC 6238 implementation computing codes against the server-issued secret (not mocked)
- [x] Every step-up grant is audit-logged. — `test_grant_is_audit_logged`
- [x] A grant for one employee never leaks to another. — browser-verified: hr_admin independently challenged after compmanager already obtained a grant

**Verification:** `manage.py check --fail-level WARNING`, `makemigrations --check --dry-run`, and `manage.py test` all pass — 403/403 tests project-wide (379 prior + 24 new: 11 `rbac_audit/test_stepup_api.py`, 5 `compensation.PayrollStepUpGateApiTests`, 2 new `ee_reporting.RemunerationImportApiTests`, plus 6 existing compensation tests whose setup needed a step-up grant added so they kept testing what they originally meant to). Frontend `tsc -b && vite build` and `oxlint` both pass. No seed_demo_data changes — deliberately: every demo login starts unenrolled, so a live demo walks the complete flow (enroll → confirm → challenge → grant), the most useful thing to show for a brand-new capability. Verified end-to-end in a real browser: `/pay-bands` showed the challenge instead of any data (confirmed no leak before step-up); enrollment, a wrong confirmation code rejected, the correct code (computed client-side via a genuine RFC 6238 implementation against the server-issued secret, not a stub) activating the device; a wrong step-up code rejected, the correct code plus a justification reason granting access; `/comp-proposals` reusing the same grant without re-challenging; a completely different user (hr_admin) independently challenged, proving no cross-user leakage; and `EEConfigurationPage`'s Employer Config/Questionnaire sections loading normally while only the Remuneration Records section showed the challenge.
